# 心迹国赛优化计划

整理日期：2026-11-13。依据：当前工作区源码、技术报告（`output/review-20261019/current-pdf-text.txt`）、`docs/plans` 下的历史计划，以及本次实测：
`unittest` 174 项全部通过（14.6 s），Ruff 对 `mental_health`、`scripts`、`tests` 无告警。

## 一、总体判断

工程完成度高于大多数校赛作品：协议严格、回退完整、测试齐全、文档可追溯。国赛评委会从三个方向追问，这三处恰好最薄：

1. **证据**：没有真人试用；安全标签由开发者自标；人工评分只有一位评阅者；机制验证只靠 3～6 组合成案例。报告第六章自己承认了这些问题，评委一定会问。
2. **算法深度**：题目里的"长期心理状态建模"和"多智能体决策"，代码里分别是关键词计数和 if/elif 规则。算法赛评委读代码或追问细节时会发现。
3. **现场体验**：普通回复要整段生成并检查后才开始播报，p95 13.84 s，再加上 TTS 时间。现场演示中的停顿很显眼。

下面按"国赛前必须做（P0）/ 强烈建议（P1）/ 有余力再做（P2）"排列。每项写明问题出在哪里、怎么改、怎样算完成。

## 二、代码层面发现的具体缺陷

### 2.1 状态估计过于粗糙（核心卖点的短板）

[state_estimator.py](../../src/open_llm_vtuber/mental_health/state_estimator.py) 的分数是 `命中词数 × 0.35`，每维只有 0 / 0.35 / 0.70 / 1.0 四档：

- 子串匹配会误命中："累"匹配"积累""累计"，"担心"匹配"不用担心"，"压力"匹配"压力测试"。
- 只有 `ContextStateEstimator` 过滤否定句，而且依赖同一组正则。
- "长期建模"（`daily_v2`）的统计设计很严谨，但它聚合的原始信号质量低。评委问"状态值怎么来的"，回答"关键词计数"会大幅削弱创新点。

### 2.2 意图识别依赖整句 `fullmatch` 正则

[intent_estimator.py](../../src/open_llm_vtuber/mental_health/intent_estimator.py) 要求整个分句完全匹配模板。下面这些自然说法都不会命中"求助"：
"能不能给我点建议""你觉得我该怎么办""有没有什么办法"。它们会掉到默认的倾听策略。而"意愿优先"正是报告里的主打机制。

### 2.3 Safety 只有正则一层

[safety_guard.py](../../src/open_llm_vtuber/mental_health/safety_guard.py)、[context_signals.py](../../src/open_llm_vtuber/mental_health/context_signals.py)：

- 隐晦表达会漏判，例如"想从楼顶下去""把药都吃了""活着没意思""想睡过去不再醒来"。"活着没意思"只会因"没意思"计入低落分，不会触发风险路径。
- 风险评估用的 65 条句子由开发者自编自标，这些句子本身就带着规则作者的偏差。保留集 25 条中误报 6 条，比例偏高。
- 输出检查也是正则，无法发现模型以委婉方式给出的有害内容。

### 2.4 危机回应没有具体求助渠道

固定危机回复只写"危机热线"，前端也没有危机资源卡片（前端源码中检索不到任何热线号码）。心理健康赛道的评委几乎一定会看这一点。

### 2.5 "多智能体"名不副实

[decision_coordinator.py](../../src/open_llm_vtuber/mental_health/decision_coordinator.py) 的协调逻辑会覆盖模型提议。历史实验中独立 Decision 模型的提议"全部为倾听"，正确路由来自本地规则（见 2026-09-22 计划 E1 记录）。产品默认配置不调用 Decision 模型。

### 2.6 响应时延

[mental_health_agent.py:350-406](../../src/open_llm_vtuber/agent/agents/mental_health_agent.py:350) 先把全部 token 收齐，做输出检查，然后才 `yield`。首句等待时间等于整段生成时间。

### 2.7 工程风险

- **本地检出停在上游分支**：源码已在公开仓库 `xinji/main`（提交 `9b5ffcc`）中，但本地 `main` 仍是上游 `992309c`，导致 `git status` 显示几百个未提交文件，容易误操作。2026-11-13 已切换到跟踪 `xinji/main` 的本地分支 `xinji-main`。
- `companion_for()` 每次请求都新建 `CompanionStore` 并执行 `CREATE TABLE IF NOT EXISTS`；`turns()` 对每个片段单独查询一次（N+1 查询）。演示数据量下无感，但评委读代码时容易被指出。
- 心理状态 SQLite 以明文存储，只有删除功能，没有"导出我的数据"。
- 前端只有 3 个测试文件，配套的 companion 组件共约 2150 行。

## 三、P0：国赛前必须完成

### P0-1 统一版本管理（已完成，2026-11-13）

本地已切换到分支 `xinji-main`（跟踪 `xinji/main`）；`.gitignore` 新增 `/output/`、`/work/` 及缓存目录。之后每完成一项优化单独提交，并推送到公开仓库，使评委看到的仓库与提交的源码包一致。
**完成标准**：`git status` 干净；公开仓库能按 README 复现启动。

### P0-2 危机支持落到实处（1 天）

- 固定危机回复中写明具体渠道：全国统一心理援助热线 12356、希望 24 热线 400-161-9995、急救 120、报警 110。提交前逐一核对官方来源，确认号码现行有效。
- 前端在收到 `crisis_support` 策略时弹出常驻的危机资源卡片，提供一键拨号（`tel:` 链接）、"联系信任的人"提示，并暂停普通对话入口，直到用户确认安全。
- 演示脚本加入一段风险输入的现场演示。
**完成标准**：风险输入后 1 秒内出现卡片；新增对应前后端测试。

### P0-3 流式输出 + 分句安全检查，降低首句时延（2～3 天）

把"整段生成→整段检查"改为"按句切分→逐句做输出检查→通过后立即送 TTS"。规则检查本身是毫秒级。整段级检查（诊断性措辞等）保留在末尾，作为补充；一旦命中，打断剩余播放并替换为安全回复。生成期间播放点头和"嗯"类语气反馈，掩盖等待。
**完成标准**：首句音频开始时间 p50 < 2.5 s；原有安全测试全部通过；新增"中途命中有害句"的打断测试。

### P0-4 升级状态与意图估计（4～6 天，算法赛的核心加分项）

用已经部署的 ORPO 4B 模型或独立 1.5B 模型做结构化抽取，一次调用输出：

```json
{"stress":0.0-1.0|null, "anxiety":..., "low_mood":..., "evidence_span":"...",
 "self_current":true, "intent":"venting|seeking_help|clarify|ending|other",
 "advice_preference":"declined|requested|unspecified"}
```

- 规则估计保留作下限：规则判定的风险等级不能被模型调低。模型调用失败时回退到规则。
- 用一次 JSON 调用同时完成意图和状态抽取。可以和 Decision 合并成一次请求，不额外增加时延。
- 建一个 300～500 句的评测集：一半自编，一半改写自公开中文心理对话数据（如 SoulChat、PsyQA 等公开语料，注意许可证）。由两名标注者独立标注，报告 Cohen's κ。分别给出规则版和模型版的维度 MAE、意图准确率和宏 F1。
- **校准实验**：系统中已有"用户自报"这一来源，可以直接计算"系统估计 vs 本人自报"的相关系数和偏差。这是现成的算法实验，能把"来源分层"从设计主张变成量化结论。
**完成标准**：新估计器在保留集上的宏 F1 明显高于规则版；报告新增一张对照表。

### P0-5 补一轮真人小规模试用（1～2 周，可与开发并行）

现有的 `trial_mode`、知情同意和独立档案工具已经齐备，缺的是执行：

- 招募 10～20 名同学，连续使用 7～14 天。签署知情同意，排除正在接受治疗或近期有高风险的人，并准备转介渠道。如果学校有伦理审查流程，走一遍。
- 测量可用性（SUS 量表）、工作同盟（WAI-SR 简版）、留存（第 3、7、14 天回访率），以及"策略是否符合我当时的需要"的逐轮主观评分。
- **不要**把 PHQ-9/GAD-7 前后测当作疗效结论。样本太小，宣称疗效反而失分。可以作为描述性基线收集。
- 访谈 5 人左右，整理 3 个真实问题和对应改进，写进报告的"迭代"部分。
**完成标准**：报告中出现真人数据，局限说明从"未开展真人试用"改为"小样本、非临床"。

### P0-6 第二位评阅者与专业审核（3～5 天，可并行）

- 已经生成的两份 330 项空白评分表（`ratings: all_null`）请第二位同学盲评，计算评分者间一致性。
- 联系学校心理中心老师审核 Safety 标签集和危机回复文案，在报告中写明"经 ×× 审阅"。这一项成本低、收益高。

### P0-7 答辩与演示准备（2～3 天）

- 固定 5～8 分钟演示脚本：倾诉 → 拒绝建议 → 主动求助 → 保存小步骤 → 回看两周趋势 → 纠正一条记录后策略变化 → 风险输入出现危机卡片。
- 录一份完整备份视频，网络或显卡出问题时立即切换。所有模型本机离线运行，Edge TTS 依赖网络，需要准备离线 TTS 备选（如 MeloTTS 或 sherpa-onnx TTS）。
- 准备问答清单，提前想好这些问题的回答："为什么叫多智能体""状态分数怎么来的""漏判怎么办""和 ChatGPT 加提示词有什么区别""隐私如何保障""有没有真人数据"。

## 四、P1：强烈建议

### P1-1 让"多智能体"站得住（3～5 天）

二选一，不要两头都做：

- **方案 A（推荐，诚实且有亮点）**：保留规则协调器，但把它描述为"约束层"。让 Safety、State/Intent、Decision 三个角色各自由模型或规则产出带置信度的提议，协调器按"安全 > 明确意愿 > 反馈 > 历史 > 模型提议"做仲裁，并输出可视化的仲裁轨迹。前端增加"本轮为什么这样回应"的展开面板。评委看得懂，也确实是多角色协同。
- **方案 B**：用规则输出加人工修订，构造 1～2 千条策略标签，微调 1.5B Decision，让模型提议本身有效。报告模型提议与最终策略的一致率。工作量更大，并且依赖 P0-4 的评测集。

### P1-2 长期状态的算法升级（3～4 天）

当前的硬门槛（≥3 个有效日、≤7 日新鲜度）可解释，但比较生硬。可以在 `daily_v2` 旁增加一个对照版本：

- 指数衰减加权均值，或带先验的贝叶斯均值（Beta 先验），给出可信区间而不是 null/非 null 两态。
- 用 CUSUM 或滑动窗口做变化检测：连续若干天上升时，提示"最近压力好像一直偏高，要不要聊聊"。这是"长期建模"最直观的用户价值。
- 系统估计和用户自报出现分歧时，以自报为准并降低系统估计的权重。
- 用已有的 14 日合成场景加真人试用数据做对照，延续现有的"可回放、确定性"风格。

### P1-3 Safety 第二层（2～3 天）

在正则之后加一个轻量分类器：中文 RoBERTa 微调，或用 4B 模型做零样本判别。只允许它**升级**风险，不允许降级，以保住"不漏判"的底线。评测集加入隐晦表达、网络用语、谐音（如"紫砂"）。如果能获取学术许可，可以引用公开的中文自杀风险数据集做外部验证。

### P1-4 前端演示体验（2～3 天）

- 趋势图标注来源、有效天数和置信区间；无数据和数值为零的状态在视觉上要区分开。
- 首次使用引导（3 步）、加载态、空态和错误态。
- 技术回放面板做成评委能一眼看懂的时间线：输入 → 安全 → 意图/状态 → 提议 → 仲裁 → 输出 → 播放回执。
- 补前端测试：危机卡片、反馈取消、小步骤状态流转。

## 五、P2：有余力再做

- `CompanionStore` 改为每个 Agent 复用一个实例，建表只执行一次；`turns()` 改为一次 JOIN 查询。
- 用 SQLCipher 或操作系统级加密保护本机数据；增加"导出我的数据（JSON）"功能，与删除功能配对。
- 多模态信号：利用 SenseVoice 已经输出的情感标签作为第四个状态来源（语音情绪）。这样能体现"数字人"相对纯文本方案的优势，实现成本也低。
- 记忆摘要：跨会话保留用户愿意保留的主题摘要（如"最近在准备考研"），让开场白能接续上次的话题。
- 一键启动脚本，加上 Docker 或便携包，降低评委复现成本。
